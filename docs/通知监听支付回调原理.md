# 通知监听实现支付回调：原理说明

> 说明业界常见的「通知监听 → 业务回调」做法，以及 Nairo 自研实现要点。  
> 本文只讨论公开的 Android 系统能力与本仓库代码，不附带任何第三方 APK。

## 1. 问题背景

个人收款码（微信 / 支付宝）通常**没有**官方实时商户回调。常见替代方案是：

1. 用户手机上已安装微信 / 支付宝；
2. 收款成功后，支付 App 会弹出系统通知；
3. 自研 App 通过系统 **通知使用权** 读取该通知；
4. 解析金额、渠道等信息后，向业务服务器发起 HTTP 回调。

该方案依赖通知文案稳定性与进程保活，适合本人商户设备上的近实时同步，**不能**替代官方商户能力（退款、分账、合规对账等）。

## 2. 总览链路

```text
支付 App 发出通知
        │
        ▼
系统 NotificationManager
        │
        ▼
NotificationListenerService.onNotificationPosted()
        │
        ├─ 过滤包名（微信 / 支付宝等）
        ├─ 读取 title / text / ticker
        ├─ 正则提取金额
        └─ HTTP GET/POST 回调业务端（如 /appPush?t=&type=&price=&sign=）
                │
                ▼
          业务服务器入账 / 发货
```

同类方案通常还包含：配置二维码扫描、通讯密钥、心跳、HTTP 重试、WakeLock 等。

## 3. 系统能力：NotificationListenerService

Android 提供官方 API：`android.service.notification.NotificationListenerService`。

关键点：

| 项 | 说明 |
|----|------|
| 声明 | Manifest 中注册 `service`，intent-filter action 为 `android.service.notification.NotificationListenerService` |
| 权限 | `android:permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE"`（仅系统可绑定） |
| 用户授权 | 必须在系统设置「通知使用权 / 通知栏读取」中手动开启 |
| 回调 | `onNotificationPosted(StatusBarNotification)` / `onNotificationRemoved(...)` |
| 内容 | 从 `sbn.notification.extras` 取 `EXTRA_TITLE`、`EXTRA_TEXT`，以及 `tickerText` |

这是**用户显式授权**后的能力，不是静默越权读取。

## 4. 支付通知如何变成「支付回调」

### 4.1 包名过滤（常见实现 观察到的目标）

- 微信：`com.tencent.mm`
- 支付宝：`com.eg.android.AlipayGphone`

还可根据通知标题辅助识别，例如「微信收款助手」「微信支付」「成功收款」等文案。

### 4.2 文本解析

通知正文常见形态（示例，非固定协议）：

- `个人收款码到账¥2.00`
- `通过扫码向你付款`
- `成功收款`

实现上一般用正则抓取 `¥` / `￥` 后的数字，得到 `price`。匹配失败则只记日志，不回调。

### 4.3 服务端推送

原实现通过 OkHttp 访问类似：

```text
{host}/appPush?t={timestamp}&type={1|2}&price={amount}&sign={md5(...)}
```

其中：

- `type`：渠道枚举（如微信 / 支付宝）
- `sign`：由通讯密钥等字段按约定拼接后做 MD5，用于防伪造
- 另有心跳接口，用于确认监控端在线

本仓库第一期**先完成通知采集与本地展示**；HTTP 回调可按你们业务协议后续接入。

## 5. 为什么必须做保活

`NotificationListenerService` 在进程被杀、省电策略过激、厂商「强制停止」后可能暂时失效，表现为：

- 听不到新通知；
- 或需重新开关通知使用权才恢复。

常见配套手段（合规、可上架前提下）：

1. **前台服务**：常驻状态栏通知，降低被杀概率；
2. **开机广播** `BOOT_COMPLETED`：开机后拉起前台服务；
3. **忽略电池优化**：引导用户关闭对本 App 的doze 限制；
4. **厂商自启动 / 后台运行白名单**：小米 / 华为 / OPPO / vivo 等需引导用户手动设置；
5. **服务被停时自检**：App 打开时检测通知使用权与监听连通性。

注意：Android 8+ 后「双进程互拉」等黑产保活已不可靠且易被商店拒绝，应以前台服务 + 用户授权为主。

## 6. 安全与合规

- 通知内容可能含付款人备注、金额等敏感信息，需本地加密存储与最小权限上传。
- 仅用于**本人商户设备**上的收款同步；勿用于未经授权监控他人设备。
- 签名校验、HTTPS、防重放（timestamp + nonce）建议服务端强制校验。
- Google Play / 国内应用商店对「通知监听」用途审查较严，需在隐私政策中披露。

## 7. 与本仓库实现的对应关系

| 常见实现 能力 | Nairo App 实现 |
|-------------|----------------|
| `NotificationListenerService` 子类 | `PaymentNotificationListener` |
| 仅微信/支付宝收款 | `PaymentHintParser.shouldCapture`（包名 + 收款关键词） |
| 本地记录 / 调试展示 | Room + 首页时间线 |
| WakeLock / 心跳 | `KeepAliveService` 前台保活 |
| 开机恢复 | `BootCompletedReceiver` |
| 扫码配置密钥 / HTTP 回调 | `AppBindConfig` + `PushSyncEngine` / `NairoApiClient` |

## 8. 手工验收清单

1. 安装 App → 打开通知使用权；
2. 启动保活前台服务，并忽略电池优化；
3. 用另一台手机向本机微信/支付宝收款码支付小额；
4. 确认 Nairo 时间线出现对应通知；
5. 强制划掉任务后等待一段时间，再支付一笔，确认仍能收到（视厂商策略而定）；
6. 重启手机，确认前台服务自动起来，监听仍有效。
